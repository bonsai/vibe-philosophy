# モデル特性 × 指示の組み合わせ最適化

## 目的

モデルの性能を単体で順位づけするだけでなく、タスク特性に応じて「モデル × 指示テンプレート × ツール・権限 × 検証方式」を選択し、6軸の評価を改善する。

**最適化単位 = モデル構成 × 指示構成 × タスククラス × 実行環境**

## 用語

- **Model Profile**: バージョン、能力、既知の弱点、速度、コスト、6軸の実測値、評価条件。
- **Instruction Profile**: 目的、成功条件、制約、例、出力形式、質問・保留条件、検証要件。
- **Task Profile**: タスク種別、難易度、曖昧さ、失敗時の損害、許容時間・費用、必要な精度と深さ。
- **Agent Configuration**: モデル、指示、ツール、権限、メモリ、検証器をまとめた実行可能な構成。
- **Evaluation Record**: 構成、タスク条件、実測値、証拠、評価者を結びつける記録。

## 最適化ループ

1. **特徴づけ**: 同じ基準タスク群でモデルを測り、得意・不得意と不確実性を記録する。
2. **タスク分類**: タスクをリスク、難易度、曖昧さ、品質要件、予算で分類する。
3. **指示候補の作成**: 目的・制約・例・手順・出力形式・検証方法の違う候補を作る。
4. **比較試験**: 同じタスクセット、同じツール条件、同じ採点基準で候補を比較する。
5. **6軸評価**: 倫理観・速度・機能・精度・コスト・深さを個別に採点する。
6. **採用判定**: 倫理ゲートと用途別最低基準を満たす候補だけを比較対象にする。
7. **最適化**: 合格候補の中から、品質・速度・費用の目的に適合する構成を選ぶ。
8. **回帰テスト**: 指示・モデル・ツール・権限を変更したら、必須テストを再実行する。
9. **監視と再評価**: モデル更新、価格変更、タスク分布の変化、失敗発生時に再評価する。

## 実験設計

- まずモデルを固定して指示を比較し、次に指示を固定してモデルを比較する。
- その後、モデル × 指示の交互作用を調べる。
- 同一タスクに対する比較では入力、ツール、権限、採点基準を揃える。
- 複数回の試行を行い、平均だけでなく分散、最悪ケース、重大失敗を記録する。
- テストセットの一部を最適化に使わず、未使用のホールドアウト評価を設ける。
- 指示候補の作成と最終評価を可能な限り分離し、過学習を抑える。
- タスク難易度が異なる結果を単純集計せず、タスククラス別に比較する。

## 指示テンプレートの構成要素

1. 役割・目的
2. 完了条件と優先順位
3. 必須制約と禁止事項
4. 利用可能な情報・ツール・権限
5. 不明点・矛盾・高リスク時の質問または停止条件
6. 出力スキーマと具体例
7. 根拠・検証・テストの要件
8. 完了報告の要件（実施済み／未実施／未検証を区別）

すべての指示を常に追加するのではなく、各要素がどのタスクで改善をもたらすかを試験する。長い指示は常に優れているとは限らない。

## 最適化の目的関数

最初に必須条件を適用する。

- 倫理上の重大失敗がない。
- 用途で必要な機能を満たす。
- 精度・深さの最低基準を満たす。
- 証拠と独立レビューが存在する。

そのうえで、合格構成間のトレードオフを選ぶ。例:

- 品質優先: 精度・深さを最大化
- レイテンシ優先: 品質閾値を満たした上で応答時間を最小化
- 費用優先: 品質閾値を満たした上で成功タスク当たり総費用を最小化
- バランス型: 速度・機能・精度・コスト・深さの複数目標を満たすパレート最適候補を提示

倫理観を通常の重み付き平均に混ぜてはいけない。倫理は制約・拒否条件として扱う。用途によって軸の重みを変更する場合も、評価前に宣言する。

## 記録スキーマ案

```yaml
experiment_id: EXP-0001
task_profile_id: TASK-0001
model:
  id: provider/model
  version: exact-version
instruction:
  id: INST-0001
  version: v1
agent_config:
  tools: []
  permissions: least-privilege
  verifier: verifier-v1
conditions:
  dataset_version: v1
  repetitions: 3
results:
  ethics:
    critical_failures: 0
    score: null
  speed:
    latency_ms: null
  capability:
    required_capabilities_passed: []
  accuracy:
    score: null
  cost:
    cost_per_accepted_task: null
  depth:
    score: null
decision:
  status: NOT_RUN
  evidence: []
  reviewer: null
```

このYAMLは記録形式の例であり、性能結果ではない。実装時には各フィールドのスキーマ検証を追加する。

## 避けるべき失敗

- 自己申告の「得意」を測定結果とみなす。
- 1回の出力だけで優劣を決める。
- 最適化に使った問題だけで合格とする。
- 速度・安さのために品質閾値を下げる。
- 長い指示が必ず深い推論を生むと仮定する。
- 異なる権限やツール構成の結果を直接比較する。
- 倫理上の失敗を平均点で隠す。
- 変更履歴を残さず指示を更新する。

## 成果物と次の実装

- Model Profile の機械可読スキーマ
- Instruction Profile の機械可読スキーマ
- Task Profile の機械可読スキーマ
- 実験マトリクスと評価結果CSV
- 6軸ゲートと交互作用分析
- 用途別の推奨構成レポート
- 指示変更ごとの回帰テスト

まずは小規模な固定テストセットでモデルと指示の組み合わせを比較し、再現性が確認できた構成だけを推奨候補にする。
